# Data Model

Source of truth: [`packages/db/prisma/schema.prisma`](../../packages/db/prisma/schema.prisma) and
the migrations in `packages/db/prisma/migrations/`. Release 0 creates **all 39 tables**; Release 0
services use the identity/access, organization, project, and audit tables. Other tables are in place
so the model can be reviewed as a whole and so later releases add behavior, not foundations.

## Conventions

| Concern | Convention |
|---|---|
| Keys | `uuid` primary keys generated by PostgreSQL (`gen_random_uuid()`) |
| Naming | snake_case plural tables/columns; Prisma models PascalCase |
| Time | `timestamptz(3)` in UTC; calendar dates as `date` |
| Money | `bigint` minor units (`*_cents`) + `char(3)` ISO-4217 currency (CHECK `^[A-Z]{3}$`) |
| Concurrency | `version int` on mutable business records (optimistic locking) |
| Deletion | No hard deletes for business records; `status`/`archived_at`; FKs mostly `RESTRICT` |
| Tenancy | `organization_id` on tenant-owned top-level records; project children inherit via `project_id` |
| History | Append-only tables + immutable revisions; audit events carry before/after diffs |

## Entity overview

```
organizations ─┬─< users (home org) ─< role_assignments >─ roles ─< role_permissions >─ permissions
               ├─< contacts
               ├─< opportunities ─< activities
               ├─< proposals ──── documents ─< document_revisions
               ├─< contracts (MSA ─< SOW/CO)
               ├─< engagements >─< engagement_projects >─< projects
               │        │                                   ├─< project_members >─ users, roles
               │        ├─< time_entries                    ├─< milestones ─< tasks ─< dependencies
               │        └─< invoices ─< invoice_lines       ├─< gates ─< gate_requirements
               │                 └─< payments               ├─< risks ─< issues, decisions
               ├─< agent_runs ─< agent_actions              ├─< change_requests ─< baselines
               └─< integrations                             └─< deliverables
approvals ── target: document_revisions XOR baselines (+ evidence revision)
audit_events (no FKs) · notifications · idempotency_keys
```

## Tables by domain

### Identity, tenancy, access
| Table | Notes |
|---|---|
| `organizations` | Every company; **each is a tenant boundary**. `kind`: ems_operator, customer, prospect, partner, vendor. `segment`: manufacturer, custom_machine_builder, robotics_integrator, automation_company, oem, other. Exactly one `ems_operator` (partial unique index). `status='archived'` ⇔ `archived_at` set. |
| `users` | Platform identity. `user_type` internal/customer/service; `home_organization_id`; `status` invited/active/suspended/deactivated; `(oidc_issuer, oidc_subject)` unique; `lower(email)` unique. Never deleted. |
| `roles` | `key`, `scope` (global/organization/project), `assignable_to` user types, `mfa_required`, `is_system`. |
| `permissions` | Catalog keys such as `organization:update`; `privileged` ⇒ MFA. |
| `role_permissions` | Role ↔ permission. Synced from `@ems/domain` for system roles. |
| `role_assignments` | Global (`organization_id` NULL) or organization-scoped grants; revocation via `revoked_at`; one active assignment per (user, role, scope). |
| `project_members` | Project-scoped role grants (project roles only); one active membership per (project, user). |

### CRM
`contacts` (with `do_not_contact` for outreach compliance; optional link to a `users` row),
`opportunities` (stage, commercial model, value, probability 0–100), `activities` (calls, emails,
meetings, notes; `actor_type` user/agent with `agent_run_id`).

### Sales and contracts
`proposals` (number, status, commercial model, document), `contracts` (MSA/SOW/PO/CO/NDA; parent
contract; `executed_at` set only by the contract-execution workflow after both parties' approvals).

### Delivery
| Table | Notes |
|---|---|
| `engagements` | EMS service under a contract: commercial model (fixed-price package, monthly retainer, milestone-based, T&M), weekly hours target, fee/rate fields, budget. |
| `projects` | The customer's equipment project (code, equipment type, site, dates). |
| `engagement_projects` | Many-to-many. **An engagement can end while its project continues.** |
| `milestones` | Planned/forecast/actual dates; optional billable amount (CHECK: billable ⇒ amount); optional link to a gate. |
| `tasks` | WBS, assignee, planned/actual dates, estimate, % complete (0–100). |
| `dependencies` | FS/SS/FF/SF with lag; no self-dependency (CHECK); cycle detection in service (R2). |

### Governance
| Table | Notes |
|---|---|
| `gates` | Ordered stage gates per project; `required_approval_level` 1–3; gate package document. |
| `gate_requirements` | Deliverable/document/approval/checklist/evidence. `satisfied` requires verifier + time; **waiving a mandatory requirement requires an approval record** (CHECK). |
| `risks` | Probability/impact 1–5 (CHECK), response strategy, owner. |
| `issues` | Severity/status; may originate from a risk. |
| `decisions` | Decision log with supersession chain. |
| `change_requests` | Cost/schedule/scope impact; CR form document; may produce a new baseline. |
| `baselines` | `(project, kind, revision)` unique; frozen JSON `snapshot` + `content_sha256`. See invariants. |
| `deliverables` | Status; document; acceptance approval. |
| `approvals` | See invariants and the [approval matrix](../business-processes/approval-matrix.md). |

### Documents
`documents` (tenant, project/engagement, type, classification) and `document_revisions`
(immutable: storage key in S3, SHA-256, size, MIME, author/agent). The current revision is the
highest `revision_number`.

### Finance
`time_entries` (1–1440 minutes; approval requires approver + time; no self-approval),
`invoices` (CHECK total = subtotal + tax), `invoice_lines` (retainer/fixed fee/milestone/hours/
expense/adjustment; time entries link to lines), `payments` (idempotency key unique; see invariants).

### AI operations
`agent_runs` (agent key/version, prompt version, scope org/project, input/output/error, model,
tokens, `cost_micros_usd`, attempt, parent run) and `agent_actions` (ordered actions: tool calls and
proposed changes, required approval level, status, linked approval).

### Platform
`audit_events` (append-only hash chain, no FKs so history survives anything), `notifications`,
`integrations` (non-secret config + `secret_ref` pointer to the secrets manager; **never secrets**),
`idempotency_keys` (per-user keys with request hash and stored response, 24 h TTL).

## Database-enforced invariants

Defined in `migrations/20261112000100_integrity_guards/migration.sql` and covered by
`packages/db/test/integrity-guards.test.ts`.

| Invariant | Mechanism |
|---|---|
| `audit_events`, `approvals`, `document_revisions` cannot be updated or deleted; audit/approvals cannot be truncated | `BEFORE UPDATE/DELETE/TRUNCATE` triggers |
| Approval time cannot be backdated | Trigger overwrites `decided_at := now()` |
| Approval must match the exact target content | Trigger compares `content_sha256` with the revision/baseline hash |
| Approver must be an active, non-service user | Trigger |
| Approvals require MFA and exactly one target; revocations reference what they revoke | CHECKs |
| Baseline cannot become `approved` without a matching, unrevoked approval; decided baselines are immutable (only approved → superseded); only drafts deletable | Trigger |
| Payment `verified` requires evidence revision + verifier + time, and the verifier is an active internal user | CHECK + trigger |
| Agents can only *execute* level-0 actions; applying a proposal that needs approval requires `approval_id` | CHECKs on `agent_actions` |
| Audit actor consistency (`user` ⇒ user id, `agent` ⇒ run id), hash formats | CHECKs |
| One EMS operator org; case-insensitive unique emails; one active role assignment / membership | Partial/functional unique indexes |
| Value ranges (probability, %, minutes, risk scores, gate levels, dates ordered, non-negative money, totals) | CHECKs |

## Historical versions

- **Documents**: immutable `document_revisions`; editing creates revision N+1.
- **Baselines**: immutable once decided; changes produce a new revision via an approved change
  request; `supersedes_baseline_id` forms the chain.
- **Mutable records** (organizations, projects, …): every change emits an audit event with
  before/after of changed fields, so any prior state can be reconstructed.
- **Approvals**: never modified; revocations are new rows.

## Indexing strategy

Foreign keys used in filters are indexed; list endpoints have composite indexes matching their
filters (e.g. `organizations(kind,status)`, `projects(organization_id,status)`,
`audit_events(organization_id,occurred_at)`, `audit_events(entity_type,entity_id)`).
`lower(name)` on organizations supports case-insensitive lookups; trigram search is a later
optimization.

## Migrations

- `pnpm db:migrate` → `prisma migrate deploy` (non-destructive; used everywhere including CI).
- `pnpm db:migrate:dev` → create a new migration from schema changes (development only).
- Never edit an applied migration; add a new one. Raw-SQL guards go in their own migration with a
  descriptive name, and get a test in `packages/db/test`.
